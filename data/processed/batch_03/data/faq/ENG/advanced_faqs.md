# Software Engineering / Development — Advanced FAQs (Edge Cases, Comparisons, Policy Interpretation)

## FAQADV-ENG-001: Feature Branch Creation and Naming: What happens if Tech Lead is unavailable to approve a feature branch?
**Category:** Edge Case / What-If | **Difficulty:** Advanced | **Access Level:** employee

**Answer:** Route it to the Tech Lead's delegate (typically the next role up the escalation chain) via MK-CodeForge, tagged 'Delegate Approval Required'; the Tech Lead is notified on return and can flag it for review within 5 business days if needed.

**Related Documents:** SOP-ENG-001-EDGE-A
---

## FAQADV-ENG-002: Feature Branch Creation and Naming: Can a feature branch be expedited in a genuine emergency?
**Category:** Edge Case / What-If | **Difficulty:** Advanced | **Access Level:** employee

**Answer:** Yes, via the expedited path: get verbal pre-approval from the Tech Lead directly, proceed with the minimum necessary action, then file the formal request in MK-CodeForge within 24 hours marked 'Emergency — Retroactive Approval'.

**Related Documents:** SOP-ENG-001-EDGE-B
---

## FAQADV-ENG-003: Feature Branch Creation and Naming: What do I do if MK-CodeForge is down and I need to submit a feature branch?
**Category:** Edge Case / What-If | **Difficulty:** Advanced | **Access Level:** employee

**Answer:** Non-urgent requests should wait for MK-CodeForge to be restored. For genuinely urgent cases, email the Tech Lead directly with the request details; once MK-CodeForge is back, enter the request and outcome retroactively, tagged 'Entered Retroactively — System Outage'.

**Related Documents:** SOP-ENG-001-EDGE-C
---

## FAQADV-ENG-004: Feature Branch Creation and Naming: What happens if my feature branch request is rejected, or I accidentally submit it twice?
**Category:** Edge Case / What-If | **Difficulty:** Advanced | **Access Level:** employee

**Answer:** Rejections always come with a documented reason in MK-CodeForge — correct the issue and resubmit, or escalate once if you disagree. Duplicates are flagged automatically and reconciled by keeping the original and closing the duplicate with a cross-reference.

**Related Documents:** SOP-ENG-001-EDGE-D
---

## FAQADV-ENG-005: Feature Branch Creation and Naming: What happens if my feature branch submission is missing required documentation?
**Category:** Edge Case / What-If | **Difficulty:** Advanced | **Access Level:** employee

**Answer:** The Tech Lead returns the request in MK-CodeForge with a specific note on what's missing rather than approving or fixing it themselves; you have about 5 business days to correct and resubmit through the same request thread.

**Related Documents:** SOP-ENG-001-EDGE-E

## FAQADV-ENG-026: If I find an old reference to the Code Review Policy that seems to disagree with what's current, which one is right?
**Category:** Policy Interpretation | **Difficulty:** Intermediate | **Access Level:** employee

**Answer:** The current version, POL-ENG-001, is always authoritative going forward. If an older cached or printed copy of the Code Review Policy disagrees with it, treat the current document as correct and check the POL-ENG-001-HISTORY document to understand exactly what changed and when.

**Related Documents:** POL-ENG-001, POL-ENG-001-HISTORY

## FAQADV-ENG-027: What's the difference between the standard Feature Branch Creation and Naming process and the emergency/expedited version?
**Category:** Comparison | **Difficulty:** Intermediate | **Access Level:** employee

**Answer:** The standard path (SOP-ENG-001) goes through Tech Lead via MK-CodeForge in the normal order. The expedited path (SOP-ENG-001-EDGE-B) is only for genuine emergencies: it requires verbal pre-approval first, immediate action, then retroactive formal filing within 24 hours — and repeated use of the expedited path for the same request type triggers a review.

**Related Documents:** SOP-ENG-001, SOP-ENG-001-EDGE-B
