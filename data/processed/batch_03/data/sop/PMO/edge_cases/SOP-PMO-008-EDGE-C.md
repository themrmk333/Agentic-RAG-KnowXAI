**Department:** Project Management / PMO

## Situation
MK-PMTrack is down, in scheduled maintenance, or otherwise unreachable, but the milestone acceptance genuinely cannot wait until the system is restored.

## Detection
Project Manager attempts to log into MK-PMTrack and receives a system-unavailable error, or has received a maintenance notification covering the relevant window (see the Communications archive).

## Decision Criteria
Project Manager first checks whether the request is time-sensitive enough to justify an off-system workaround, or whether it can simply wait for MK-PMTrack to be restored (the default expectation).

## Steps

1. Project Manager confirms MK-PMTrack is genuinely unavailable (not just a personal connectivity issue) by checking with a colleague or the IT status page.
2. For non-urgent milestone acceptance requests, Project Manager waits for MK-PMTrack to be restored and submits normally — this is the default and preferred path.
3. For genuinely urgent requests, Project Manager documents the request details (who, what, why, when) in an email to the Program Manager instead of the system.
4. The Program Manager reviews the emailed request using the same criteria they would apply inside MK-PMTrack, and replies with an approval/rejection decision in writing.
5. Once MK-PMTrack is restored, Project Manager or the Program Manager re-enters the request and its outcome into MK-PMTrack retroactively, referencing the original email for the audit trail.
6. MK-PMTrack's record is tagged 'Entered Retroactively — System Outage' so reporting doesn't mistake the entry date for the actual request date.

## Responsible Role
Project Manager

## Approval
Program Manager

## Escalation
Project Coordinator -> Project Manager -> PMO Lead -> PMO Director

## Expected Result
The milestone acceptance is actioned without waiting for system restoration when genuinely urgent, while still ending up fully and correctly recorded in MK-PMTrack once it's back online.
