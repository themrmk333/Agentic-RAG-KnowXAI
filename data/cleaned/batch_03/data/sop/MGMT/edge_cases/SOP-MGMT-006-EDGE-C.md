## Situation
MK-ExecDash is down, in scheduled maintenance, or otherwise unreachable, but the board report genuinely cannot wait until the system is restored.

## Detection
Senior Manager attempts to log into MK-ExecDash and receives a system-unavailable error, or has received a maintenance notification covering the relevant window (see the Communications archive).

## Decision Criteria
Senior Manager first checks whether the request is time-sensitive enough to justify an off-system workaround, or whether it can simply wait for MK-ExecDash to be restored (the default expectation).

## Steps

1. Senior Manager confirms MK-ExecDash is genuinely unavailable (not just a personal connectivity issue) by checking with a colleague or the IT status page.
2. For non-urgent board report requests, Senior Manager waits for MK-ExecDash to be restored and submits normally — this is the default and preferred path.
3. For genuinely urgent requests, Senior Manager documents the request details (who, what, why, when) in an email to the CEO Office instead of the system.
4. The CEO Office reviews the emailed request using the same criteria they would apply inside MK-ExecDash, and replies with an approval/rejection decision in writing.
5. Once MK-ExecDash is restored, Senior Manager or the CEO Office re-enters the request and its outcome into MK-ExecDash retroactively, referencing the original email for the audit trail.
6. MK-ExecDash's record is tagged 'Entered Retroactively — System Outage' so reporting doesn't mistake the entry date for the actual request date.

## Responsible Role
Senior Manager

## Approval
CEO Office

## Escalation
Manager -> Director -> Vice President -> CEO Office

## Expected Result
The board report is actioned without waiting for system restoration when genuinely urgent, while still ending up fully and correctly recorded in MK-ExecDash once it's back online.
